### Red flags for AutoApply

1. **`agent_helpers.py` is shared, not project-scoped.** If we have multiple agents adding helpers (CareerOps, AutoApply, anything else), they all write into the same `agent-workspace/agent_helpers.py`. Could get cluttered. Mitigation: namespace helpers with prefixes (e.g. `autoapply_*`) or use a separate repo clone per project.
2. **Auto-update behavior.** `browser-harness` prints `[update available]` daily; the agent is *instructed* to run `--update -y` on its own without asking. Our integration could break silently if upstream changes API. Pin the version (clone at a tag, or disable the update behavior) before relying on it for production AutoApply.
3. **Way 1 popup fragility.** The "Allow remote debugging?" dialog appears on Chrome 144+ first-attach (and sometimes later). For unattended AutoApply runs, plan to use Way 2 (`--remote-debugging-port` + custom `--user-data-dir`) — which means a separate Chrome profile that doesn't inherit your logged-in ATS sessions. Trade-off to think about.
4. **`BROWSER_USE_API_KEY` not set.** Optional today (we used local Chrome) but needed for cloud browsers, profile sync, and headless/proxy/captcha cases. You asked to set this up interactively — see open question below.
5. **No PATH integration.** `~/.local/bin` not on PATH. Not blocking, but every invocation needs the absolute path. Run `uv tool update-shell` to fix permanently.
